# garnet-unlockbl

> **仓库定位已变更**：这里原本是一套"红米 Note 13 Pro 5G 强制解锁 BL"的发包脚本，
> 那个版本是从网上帖子转述、代码未经验证，**不可能工作，且对设备有风险**。
> 现在这里是**对那套说法的静态核查工具**：只读镜像、不发包、不碰设备。

起因：酷安用户「旋冰狼and」发了一篇《红米Note13Pro (SM7435) 底层 Fastboot 堆溢出 0day，
理论上可硬解 BL，找人实测》，配套的 Python 脚本通过 USB 把一段"伪造长度头 + 64KB 载荷"
写进 fastboot 端点，号称能改掉解锁标志位。这份仓库最初把那篇帖子的文字和代码
转述成了可运行脚本——但转述过程中丢失、篡改、臆造了关键细节，导致脚本必然失败。

与其继续维护一个不工作的"工具"，不如把它变成能回答问题的东西。

## 这个工具做什么

给一份 ABL 镜像（`abl_a` 分区 dump），在没有手机、不联网的情况下回答：

| 问题 | 工具给出的答案 |
| --- | --- |
| 帖子里指认的 `08 c3 5e b8 / 00 11 00 11` 到底是不是 `ldr w8,[x24,#-0x14] / add w0,w8,#4`？ | 逐字节解码，给出真实指令 |
| 镜像里有没有读取解锁标志位的 `ldrb`？目标地址是多少？ | 找 `adrp/add/ldrb` 组合并算出地址 |
| "oem unlock"/"unlock" 字符串被哪段代码引用？（定位处理函数） | 扫描 `adrp+add` 交叉引用 |
| 帖子里那三个"标志位地址"（0xd99d5 / 0xd99d7 / 0x99dd7d）和 `0x40000000` 在不在镜像里？ | 直接判断在/不在 |
| 传输层的 `FASTBOOT` + `FFFFFFFF` 包格式对不对？ | 协议事实判定（工具本身不发包） |

支持输入：裸二进制、ELF64（AArch64，按程序头做 VA 映射）、
Android boot image、XZ、裸 LZMA（`5d` + 4 字节字典大小）、gzip。

## 用法

```bash
python analyze_abl.py abl_raw.img                 # 分析真实镜像
python analyze_abl.py abl_raw.img --json r.json   # 附带机器可读结果
python analyze_abl.py abl_raw.img -v              # 列出全部候选，不只关注的
python analyze_abl.py bl.bin --base 0x9fc00000    # 裸二进制手工指定加载基址
python analyze_abl.py --demo                      # 内置合成样本，先看报告长什么样
python analyze_abl.py --demo elf                  # 同上，走 ELF/VA 映射路径
```

只依赖 Python 3.8+ 标准库，`pip install` 什么都不需要。

自测：

```bash
python tests/selftest.py     # 24 项断言，含 raw / ELF / LZMA 三条解析路径
```

## 拿镜像

需要 root 才能 `dd` 出 `abl_a`（这本身也是原帖逻辑的破绽：能 root 就不需要这套解锁了）。
没有设备时，也可以直接解压官方 fastboot 包（`abl.elf` 通常在 `images/` 目录里），
不碰手机就能分析。**请不要用别人网盘里的"payload"文件做任何事。**

## 报告怎么读

每条结论带一个标记：

- `✗` 与事实不符，或被证伪
- `⚠` 发现了相关指令/序列，但和帖子描述不一致
- `✓` 找到了对应证据（**不等于**漏洞成立）

最后一段会明确写：静态分析**能证伪，不能证实"可利用"**。找到 `ldur w8,[x24,#-0x14]`
只能说明镜像里有这条指令，不能说明长度确实没校验、不能说明缓冲区是 64KB、
更不能说明能拿到控制流。

## 已知的、被证伪的说法

详见 [docs/findings.md](docs/findings.md)，摘要：

1. fastboot 协议里没有 `FASTBOOT` 魔术头；包格式是 4 字节大端长度 + ASCII 命令。
   `FAST` 会被读成长度 `0x46415354`（约 1.18 GB）。
2. 原帖三个标志位地址互不相同，且都不在任何镜像映射范围内。
3. `SHELLCODE_ADDR = 0x40000000` 是凭空写的，载荷落在接收缓冲区，运行时地址未知。
4. "分配 0 字节却拷贝 64KB"在逻辑上不成立——分配长度和拷贝长度是同一个值。
5. "通用篇"要求先用漏洞拿到临时 root 才能 dump `abl_a`，而 root 又依赖 BL 解锁，构成循环。
6. 原始脚本找不到设备时会退到 `05c6:9008`（高通的 **EDL 紧急下载模式**，走 Sahara/Firehose），
   往里发 fastboot 包毫无意义。
