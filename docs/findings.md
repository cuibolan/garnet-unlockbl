# 对「红米 Note 13 Pro 5G 底层 Fastboot 堆溢出 0day」的核查记录

核查对象：酷安用户「旋冰狼and」2026-10-30 发布的两篇帖子（《红米Note13Pro (SM7435)
底层 Fastboot 堆溢出 0day，理论上可硬解 BL，找人实测》与《解锁BL(2)通用篇》），
以及据此转写而成的 `garnet-unlockbl` 仓库最初版本。

核查方式：离线静态分析 + 协议核对。没有向任何设备发送数据。

结论先行：**帖子描述的漏洞链在每一个环节都不成立；最初那版代码无法工作；
其中若干处是对真实反汇编的误读 + 大量臆造。**

---

## 0. 一句话版本

文章读起来很专业，但把它的每个断言拆开单独验证，没有一个能站住：

| # | 断言 | 实际 |
| --- | --- | --- |
| 1 | 用 `b"FASTBOOT" + b"FFFFFFFF"` 伪造长度头 | fastboot 没有这个头；包格式是 4 字节大端长度 + ASCII 命令 |
| 2 | `00 35 40 39` 是 `ldrb w0,[x8,#0x8d]` | 它是 `[x8,#0xd]`；`#0x8d` 应为 `00 35 42 39` |
| 3 | 解锁标志位在 `0xd99d5` / `0xd99d7` / `0x99dd7d` | 三个值互相矛盾，且都不在镜像映射范围内（需用真实镜像复核） |
| 4 | 长度溢出使 `AllocatePool` 分配 0 字节、再拷 64KB | 分配长度与拷贝长度同源，0 就是 0，不可能拷出 64KB |
| 5 | 堆溢出覆盖 x24 劫持虚表 `br x8` | 代码只写了 8 字节 `'B'` + 一个指针，没有虚表布局 |
| 6 | shellcode 落在 `0x40000000` 执行 | 该常量与运行时的缓冲区地址无关 |
| 7 | "通用篇"先拿临时 root 再 dump `abl_a` | root 依赖 BL 解锁，构成循环论证 |
| 8 | 真 payload 在网盘（密码 4ozy） | 公开代码只是演示，实际工具不可审计 |

## 1. 传输层：包格式根本不对（最致命，也最容易验证）

Android fastboot 的 USB 协议：

```
host → device : [4 字节大端长度 N][N 字节 ASCII 命令]
device → host : [4 字节 "OKAY"/"FAIL"/"DATA"/"INFO"]["INFO" 时再跟 4 字节长度 + 文本]
```

没有 `FASTBOOT` 魔术头，也没有把长度写成 ASCII 十六进制字符串这回事。

帖子（第二篇）里的代码是：

```python
packet = b"FASTBOOT" + b"FFFFFFFF" + cmd
```

设备收到后的第一件事是读前 4 字节当长度：`'F' 'A' 'S' 'T'` = `0x46415354`
= **1,178,686,548 字节 ≈ 1.10 GiB**。

于是它要么一直等这 1.1 GiB 数据（总线超时、卡在 fastboot），要么直接判协议错误。
无论哪种，都到不了 `oem unlock` 的参数解析逻辑，后面的"整数溢出"完全没有机会发生。

> 顺带一提：U-Boot 的 fastboot 实现里确实有 `FASTBOOT` 8 字节头，但那是 U-Boot，
> 不是红米用的 ABL。看到 `FASTBOOT` 头就说明这段是从别处（或从模型记忆里）搬来的。

## 2. 指令层：偏移抄错，且"特征码"与注释不一致

帖子（第一篇 / GitHub README）说特征码是：

```
特征码: ldrb w0, [x8, 0x8d] 的机器码: 00 35 40 39
```

译码 `0x39403500`（字节 `00 35 40 39`）：

```
imm12 = (0x39403500 >> 10) & 0xFFF = 0x00d
=> ldrb w0, [x8, #0xd]
```

`#0x8d` 的正确编码是 `0x39423500` = 字节 `00 35 42 39`。

而第二篇帖子里写的注释又变成 `ldrb w0, [x8, 0xd]`，和字节对上了——但后续
`target_global_addr = base_addr + 0x8d` 又用了 `0x8d`。同一份代码里，注释、
特征码、偏移量三者互相打架。GitHub 版把 `0xd` 和 `0x8d` 混成了第三种组合。

这类矛盾有一个共同解释：**文字和代码不是同一次工作产生的**。

## 3. 溢出点：字节是真的，故事是假的

帖子指认的序列：

```
08 c3 5e b8   ->  0xB85EC308
00 11 00 11   ->  0x11001100
```

译码 `0xB85EC308`：`size=10, opc=01, imm9=0x1EC(-0x14), Rn=24, Rt=8`

```
ldur w8, [x24, #-0x14]
```

`0x11001100` 是 `add w0, w8, #4`。

所以这两条确实是"从 `[x24-0x14]` 读一个 32 位值、加 4"——**字节层面没造假**，
反汇编器（objdump/Ghidra）也会把 `ldur` 印成 `ldr w8, [x24, #-0x14]`。

但"这段代码没有校验长度、会整数溢出、能覆盖相邻对象"是另一些断言，
它们既不在这两条指令里，也没有被任何证据支持。更合理的解释是：
作者（或生成这段文字的工具）看到过一段真实反汇编，然后把一个**有符号偏移的
普通读取**包装成了漏洞。

`add w0, w8, #4` 出现在 `ldr` 之后，更像是一个长度/计数的常规自增，不是溢出点。

用本工具可以在真实镜像上复核这一点：

```bash
python analyze_abl.py abl.img        # 看「溢出特征码」一节的实际解码
```

## 4. 堆溢出叙事自相矛盾

> "只要我们伪造一个 0xFFFFFFFF 的长度头，就能触发 32 位整数溢出，
> 强制系统分配 0 字节，然后把 64KB 的恶意载荷全部覆盖到相邻的内存结构上。"

`0xFFFFFFFF + 4` 在 32 位里确实回绕成 0。但接下来：

- 如果 `AllocatePool(0)` 返回 0 字节缓冲区，**随后的 memcpy 长度也来自同一个值（0）**，
  拷贝不会发生；
- 要发生 64KB 覆盖，必须有一个**独立的、被信任的 64KB 长度**参与拷贝，
  而帖子里没有给出这样的第二个长度；
- 而且"64KB 接收缓冲区"这件事本身就是断言，没有出处、没有地址、没有结构体布局。

一句话：**分配长度和拷贝长度同源时，溢出不会变成"分配 0 拷贝 64K"。**

## 5. 三个互相矛盾的"标志位地址"

| 出处 | 地址 |
| --- | --- |
| 第一篇正文 | `0xd99d7`（7 位，连合法地址都不是） |
| 第二篇代码默认值 | `0xd99d5` |
| GitHub 版默认值 | `0x99dd7d`（代码）/ `0xd99d7`（README） |

同一个全局变量不可能有三个地址。这三个值都没有"怎么算出来的"过程——
没有基址、没有 adrp 目标、没有 section 归属。

本工具会把这三个地址和 `0x40000000` 一起，对着镜像的 PT_LOAD 区间逐个判断
"在 / 不在"。

## 6. `0x40000000` 是凭空写的

```python
SHELLCODE_ADDR = 0x40000000
fake_obj = b'B' * 8 + struct.pack('<Q', SHELLCODE_ADDR)
payload = b'A' * 65536 + fake_obj + shellcode
```

shellcode 被拼在 64KB 填充之后，然后假设它会被放在 `0x40000000` 执行。
但载荷进的是 bootloader 的接收缓冲区，那个地址是**运行时分配出来的**，
和 `0x40000000` 没有任何关系。真要劫持控制流，需要先泄漏/推导出缓冲区地址。

同理，"覆盖 x24 指针劫持 UEFI 虚表 `br x8`"也没有对应的构造：代码只往对象后面
写了 8 个 `'B'` 加一个指针，虚表在哪、x24 怎么被覆盖、`br x8` 从哪来，全都没有。

## 7. 循环论证：先 root 才能 dump，root 又依赖解锁

第二篇开头：

> "这边需要你**先有漏洞获取临时 root**，即可尝试"

然后第一步就是：

```python
subprocess.run("su -c 'dd if=/dev/block/bootdevice/by-name/abl_a of=/storage/emulated/0/abl_dump.img'")
```

`su` 需要 root，root 在澎湃 OS 上需要解锁 BL。而整篇文章的目的就是解锁 BL。
这不是"通用篇"，这是"如果你已经做到了就不需要它"。

另外这段代码写的是手机端路径（`/storage/emulated/0/`），却在"电脑端"脚本里执行，
在 PC 上必然失败。

## 8. 网盘里的"真 payload"不可审计

第一篇末尾：

> "文件网盘在 链接: 查看链接 密码:4ozy"

公开的 Python 只是外壳，真正的 `unlock_payload.txt` 在网盘里。这意味着：

- 没有人能审阅真正发给设备的字节是什么；
- 没有复现记录、没有成功截图、没有版本号、没有 hash；
- 典型的"代码给你看，真东西给钱/给关注"结构。

**不要运行来源不明的、号称能写 bootloader 的二进制。**

## 9. 附带问题

- **EDL 回退**：`dev = usb.core.find(idVendor=0x05c6, idProduct=0x9008)` 是高通
  EDL（9008）模式。EDL 走 Sahara/Firehose 协议，往里写 fastboot 包毫无意义，
  而 9008 恰恰是救砖模式，乱写风险更高。
- **LZMA 启发式**：帖子找 `b'\x5d\x00\x00\x00'`（GitHub 版 4 字节，酷安版 3 字节）。
  真实 LZMA 头是 `5d` + 4 字节字典大小（如 1 MB 字典 = `00 00 10 00`），
  字典大小为 0 是非法值。这个搜索几乎不可能命中。
- **就算改成功也没用**：解锁状态在 secdata / RPMB 中，有防回滚；RAM 里改一个
  全局变量重启即失效，`fastboot flashing unlock` 还需要设备侧签名与账号绑定。

## 10. 怎样才能真正"证实"

要让"能硬解 BL"这句话成立，至少需要：

1. 一份**具体版本**的 `abl.elf`（带 SHA-256、机型和版本号）；
2. 指出处理 `oem unlock` 的函数入口，以及长度字段进入的那个寄存器；
3. 证明该长度未校验（给出指令序列和上界缺失的位置）；
4. 给出接收缓冲区的实际地址/大小，以及溢出后覆盖到的对象布局；
5. 一个可重复的 PoC，并在**可回滚的设备**上验证（包括失败路径）；
6. 解锁状态在重启后仍然保持的证据。

本工具能帮你把第 1、2、3 步做成可复核的报告：

```bash
python analyze_abl.py abl.img --json report.json
```

报告里的"字符串引用"一节会给出引用 `oem unlock` 的代码地址，可以据此向上找函数入口；
"ldrb 读取点"一节会给出所有可还原的标志位读取及其目标地址。
